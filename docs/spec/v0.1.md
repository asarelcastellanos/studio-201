# Spec v0.1

Status: approved 2026-11-19, revised 2026-11-19 at the v0.1 restart (D32 to D43). Repo: `asarelcastellanos/studio-201`, public. Pane design: [design/pane-pass-1.html](../design/pane-pass-1.html), approved 2026-11-19.

## Goal

The smallest Studio 201 that runs the trial. It installs on any Mac, sets up a product board, shows session usage and limits, shows agents working, keeps agents on their models, and keeps main safe. The process skills (spec, plan page, review and QA loop) come in 0.2 and the design skills in 0.3. During the trial, the process runs by hand.

## How to read a claim

Each claim is one testable sentence. "I said" quotes the request it came from. "Proof" says how it is shown to work. "Assumes" links to the assumptions below.

QA proves each claim in a real session, with a screenshot or the command output. The QA runner saves the evidence in `qa/v0.1/`, posts it on the claim's issue with a one-line result, and closes the issue. A unit test is written only when the claim names the reason, and today only C6 does. There are no integration tests or test suites.

## F5 Team and policy

**C13.** Each team role shall have an agent file with its model pinned (Sonnet or Haiku) and a tool list. Read-only roles can't edit files.
- I said: "specialized sub agents"
- Proof: QA. Check each role's transcript shows the pinned model. A read-only role trying to edit is refused. F2's QA adds the check that the pane shows the right model.

**C14.** While the policy is on, the main session shall not edit code itself. It shall be refused with a message to delegate. Code is any file except `.md` files and files in the session's scratchpad.
- I said: "a core orchestrator"
- Proof: QA. Ask the main session to edit a code file, then a screenshot of the refusal. Then it edits a `.md` file and a scratchpad file, and both go through. A list of bypass attempts (shell redirects, `sed -i`, `git -C`, wrappers) is each refused, with the output saved.

**C15.** Before Claude merges into main, it shall give me a review package and ask me to approve the merge. It merges only after I approve. Subagents can't merge into main at all.
- I said: "it should just ask me to review it and approve it. once i approve it is free to merge to main"
- Proof: QA. The main session tries `gh pr merge` on a test PR into main. A screenshot shows the approval prompt, and the merge runs only after I approve. A subagent trying the same merge is refused. Bypass attempts (`gh api`, `git push` with `HEAD:main`) are each caught, with the output saved.
- Assumes: S5

**C16.** Agents shall work on `issue/<n>-<name>` branches, open PRs into `feature/<name>`, and squash merge them there. A feature that passes review and QA shall merge into `release/v<version>`. Only the release branch merges into main, through C15.
- I said: "one branch that will be the branch that gets merged to main"
- I said: "from release/v0.1 when it is ready and everything looks good it should just ask me to review it and approve it"
- Proof: QA. The trial run's own git history.

**C18.** Code shall have no comments. A check fails any change that adds one, and runs before every PR.
- I said: "no comments. let's just have no comments."
- Proof: QA. A test change that adds a comment fails the check, with the output saved.

## Spec assumptions

| ID | Assumption | For | Against |
|----|------------|-----|---------|
| S1 | 0.1 supports macOS only. | It's where I work. Less to test. | Windows users of the public repo wait. |
| S2 | Codex gets the shared rules but not the mods or hooks, which are Claude Code features. | No extra work in 0.1. | Codex sessions don't get the meter or policy. |
| S3 | The repo installs as a Claude Code plugin marketplace. | One command, standard updates. | Mods depend on the plugin system, which may still change. |
| S4 | Setup is a script using `gh`, not a GitHub Action or app. | Runs locally, no secrets in CI. | Needs `gh` logged in with the project scope. |
| S5 | I approve merges into main at Claude Code's permission prompt. No `/approve` until the inbox in 0.4. | Keeps 0.1 small. Approval stays in the terminal. | GitHub doesn't enforce it, because the PRs are under my account (D8). |
| S6 | The trial builds Studio 201 with today's tools, following the process by hand. | Tests the process before automating it. | Steps that 0.2 automates are slower now. |
| S7 | Update pulls from main, not tagged releases. Main only changes when I approve a release merge. | Approved features reach every Mac right away. | No way to stay on an older version. Tags could come with 1.0. |
| S8 | Update replaces Studio 201's own files only. Personal `~/.claude` settings, memory and other plugins stay. Install adds one import line to `~/.claude/CLAUDE.md`. | Safe to run any time. | Hand edits to installed Studio 201 files get overwritten. |
| S9 | Install turns off the claude-workbench monitor and model-policy mods. The workbench stays on disk. | No duplicate panes or clashing rules. | Going back means turning them on by hand. |

Pane assumptions A1 to A11 are in [decisions.md](../decisions.md) and the pane design page.
