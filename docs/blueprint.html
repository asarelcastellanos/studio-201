Studio 201 blueprint

A new repo, separate from claude-workbench. You manage, Opus 5.5 orchestrates, and agents work like a software team on a GitHub board. Terminal first. This is design pass 1: content and layout only, in grayscale on purpose. You or a human designer add color, type and taste in pass 2.

Updated 2026-11-19.

Decided

Main session: Opus 5.5. Fable 5.2 or Codex give a second opinion when you ask.
Plans: an HTML page for you, with markdown source in the repo for agents.
Tools: build on existing tools, vendor the parts we want, and write our own in a fresh repo.
Tracking: GitHub Issues and Projects are the default kanban. Agents move cards and you watch.
Proof: QA evidence first. Automated tests only when they have a stated reason.
Review + QA: one loop. Findings become issues, get fixed, and are re-checked.
Start with: this blueprint, then a design pass, then build.
Name: Studio 201.
Design pass 2: you or a human designer.
GitHub identity: agents act as you and write in first person, as you. The board's Agent field records which agent did the work, for you only.
Boards: one Project per product.
Interface: terminal first, with our own mods for the board, agents and approvals.
References: no Mobbin. Design references are screenshots you drop in a folder or URLs you name.
Repo visibility: never assumed. Every new app asks public or private. Studio 201 itself is public.
Design timing: pass 1 (grayscale screens and architecture) gets a walkthrough and your approval, then v1 is built on it. Pass 2 (final design, by you or a designer) lands at the end, before the public 1.0 release.
Web default: Tailwind and shadcn/ui, unless a project says otherwise.
Assumptions: every conceptual decision or major assumption an agent makes gets logged with its framing, pros and cons, so you can agree or argue.

StepRule
Feature branchfeature/<name>, cut from main, one per feature.
Issue branchesissue/<number>-<name>, one per issue, each in its own worktree. They can't live under feature/<name>/ because git refuses a branch nested inside another branch's name.
Issue PRsInto the feature branch. Squash merged after the Review + QA loop passes. Agents merge these, and small related issues can share one PR.
Keeping currentMain merges into the feature branch whenever main moves, so the final merge has no surprises.
Feature PRFeature branch into main, squash merged, so main gets one commit per feature. Only you approve it.
EnforcementAgents act as your GitHub account, and GitHub won't let you approve your own PR, so GitHub can't enforce your approval. A hook blocks any agent from merging into main, and only your /approve merges it.
VersionsSemantic versioning, major.minor.patch. A feature bumps minor, a fix bumps patch. 0.x until design pass 2, then 1.0 is the public release. One GitHub milestone per version.
Feature flagsOff by default. Feature branches already keep unfinished work out of main. Use a flag only when a feature has to ship dark, such as a staged web rollout.

Mods

You work in the terminal, so the mods bring the board, the agents and your approvals into it. In a terminal, a mod can draw a pane beside the chat (when the window is about 144 columns or wider, or when you open it), a row above the prompt, a status line, toasts, extra lines under a tool call, and slash commands. It can also block or rewrite tool calls, run gh on a timer, and add to the system prompt. Rules that need code live in mods instead of shell hooks.

Type and color

Fonts and color give away generated UI faster than anything else. Both get rules the agent must follow and a script that checks the result.

Type

  • Pick fonts from the subject and mode in DESIGN.md, never by habit. Inter, Space Grotesk, and serif-plus-cream are refused unless the brief asks for them.
  • Two families at most: a display face used sparingly and a body face. Add a mono only for data or code.
  • Pair by contrast in structure, such as a geometric sans with a humanist sans, not two faces that look alike.
  • A fixed type scale (for example 1.25 ratio), 3 or 4 weights at most, body 16px or larger, 65ch line length.
  • Native apps use the system font: SF Pro on Apple, Segoe UI Variable on Windows. Custom faces only for brand moments.
  • Tabular numbers in tables, balanced headings, slight negative tracking on large headings only.

Color

  • Build palettes in OKLCH so equal steps look equal. A 10-step scale for neutrals and for the accent.
  • Tint neutrals slightly toward the accent hue. Pure gray reads as unconsidered.
  • One accent, used for action and focus. Most of the screen is neutral.
  • Success, warning and error are separate from the accent and always paired with text or an icon, never color alone.
  • Dark mode is designed, not inverted: lift surfaces with lighter grays instead of shadows, and lower saturation.
  • Refuse: purple-blue gradients, neon on black, gray text on colored backgrounds, more than one saturated hue competing.
